# Recorder

Recorder is a personal project and notes application. The app supports GitHub login for one configured account, project CRUD/search/tag management, and formatted note CRUD. Search covers client and project names; note-body search remains planned.

## Stack

- Node.js 24.21.0 (`.node-version`; SQLite support requires Node 24.15 or newer)
- SvelteKit 2.70.3 with adapter-node 5.5.7, Svelte 5.57.1, TypeScript 5.9.3, and Vite 7.3.6
- Tiptap 3.31.4 for the formatted note editor; `sanitize-html` 2.18.0 sanitizes note HTML on the server
- SQLite through Node's built-in `node:sqlite` `DatabaseSync` API
- Drizzle ORM 0.45.3 schema declarations and Drizzle Kit 0.31.11 SQL migration generation
- Vitest 5.0.3

The plan proposed `better-sqlite3`. On Windows, its install fell back to node-gyp and could not build because this development environment has no Visual C++ workload. This foundation uses Node's built-in SQLite instead, avoiding a platform-specific native dependency. Drizzle schema declarations generate reviewed SQL migrations; runtime migration application executes those versioned SQL files through `node:sqlite` and records SHA-256 hashes in `__app_migrations`.

Node documents `node:sqlite` as a release candidate in the Node 24 line, and Node may emit an experimental-feature warning when it is used ([Node.js SQLite API](https://nodejs.org/api/sqlite.html)).

## Local setup

Install Node.js 24.21.0 and npm, then run:

```powershell
npm ci
Copy-Item .env.example .env
npm run db:migrate
npm run dev -- --host 127.0.0.1 --port 3000
```

The default local database is `./data/recorder.sqlite`. That file and the `data/` directory are ignored by Git. Check the server with:

```powershell
Invoke-RestMethod http://127.0.0.1:3000/health
```

The endpoint returns `{"status":"healthy"}` only when SQLite responds to `SELECT 1`; it returns a generic `503` response on failure.

## Configuration and scripts

`.env.example` documents the database, runtime, and Auth.js settings. Set `AUTH_SECRET` to a random secret of at least 32 characters, `AUTH_GITHUB_ID` and `AUTH_GITHUB_SECRET` to the OAuth app credentials, and `GITHUB_ALLOWED_USER_ID` to the numeric GitHub account ID permitted to use the archive. Missing or malformed allowlist configuration denies access. Keep `.env` out of version control.

Create a GitHub OAuth App with callback URL `http://127.0.0.1:3000/auth/callback/github` for local development and the exact HTTPS origin plus `/auth/callback/github` for the deployed Render service. Do not use callback wildcards. On Render, set `AUTH_SECRET`, `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET`, `AUTH_TRUST_HOST=true`, and `GITHUB_ALLOWED_USER_ID` in the Dashboard; do not put credentials in `render.yaml`. Auth.js uses its built-in OAuth state and callback handling. Logout is a POST action. `/health`, login, and Auth.js callback paths remain public; project loads and actions recheck the session and allowlisted ID server-side.

Production requires an absolute `DATABASE_PATH` below `PERSISTENT_DISK_MOUNT_PATH` (default `/var/data`) and an existing mount directory. The application fails closed when either condition is not met.

Available npm scripts: `dev`, `build`, `preview`, `start`, `check`, `test`, `db:generate`, and `db:migrate`.

```powershell
npm run check
npm test
npm run build
npm run db:generate # after schema changes; review the generated SQL
npm run db:migrate  # applies committed SQL migrations
```

## Render deployment

`render.yaml` defines a paid, single-instance Node web service, health check `/health`, build and start commands, and a 1 GB persistent disk mounted at `/var/data`. The start command applies migrations before the server accepts traffic. The database file is `/var/data/recorder.sqlite`.

Render persistent disks preserve only data beneath their mount path. Services with a disk cannot scale to multiple instances. Review the service and disk cost in Render before provisioning. The blueprint prepares the deployment configuration; no Render deploy or redeploy persistence check has been run yet. Create/verify the disk in the Render Dashboard if the blueprint does not provision it for the account.

## Project status

The schema includes projects, notes, tags, and project-tag associations with uniqueness, status checks, foreign keys, and cascade deletes. Project uniqueness compares exact stored strings; CRUD trims values and preserves that case-sensitive database rule. The app supports project create/read/update/delete, status and contact fields, reusable tags, case-insensitive partial search over client/project names, and note create/read/update/delete. Notes store allowlisted HTML generated by the editor; the server sanitizes both writes and values returned for rendering. Note timestamps are assigned in SQLite and listed newest first. Note-body search is not implemented. Render deployment configuration is prepared, but deployment, OAuth callback verification, and persistent-disk redeploy validation have not been performed.
